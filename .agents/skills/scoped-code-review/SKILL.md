# 定向代码审查 (Scoped Code Review)

一个结构化的 Skill，用于对用户确认的特定范围进行代码审查。该审查结合了**局部微观视角**（单行/函数/模块级质量）与**宏观视角**（审查的代码如何融入更大的架构），并特别强调捕捉低价值的复杂性——即那些技术上可以“运行”但增加了不必要的间接性、冗余抽象或维护负担的代码。

## 🛑 护栏：确认审查范围（强制门控）

**在审查范围明确之前，绝对不要开始任何分析或工具调用。**

只有当用户指定或你可以通过上下文高度置信地推断出以下一项或多项时，才视为范围已确认：

- 具体的文件路径、目录或函数/类/模块名称。
- 具体的 git diff、PR 或 commit 散列值。
- 当前上下文中唯一存在的、用户刚刚粘贴/上传的单个代码块或文件。

**范围不明确时的操作**：如果用户仅说“帮我审查代码”而没有给出明确目标，**立即停止**。使用 `ask_user_input_v0` 工具（如果可用）或直接询问：“请问您希望我审查哪些具体的文件、文件夹或 diff 变更？”

_如果范围明确，请简要复述（例如：“正在审查 `src/utils/payment.ts` ...”）并进入步骤 1。_

## 执行工作流

### 步骤 1：收集上下文（工具调用）

不要盲目地只看片段。使用文件读取和搜索工具来收集必要的上下文：

1. **完整阅读目标**：完整阅读目标文件或 diff 内容。
2. **情境化分析**：使用 `grep` 或文件搜索工具，快速浏览兄弟文件或调用方。理解项目已有的约定（命名风格、错误处理、分层设计）。
3. **检查规范契约**：查看项目中的 lint 配置（如 `eslint/ruff`）、`README.md` 或架构文档，建立对项目隐式风格契约的认知。
   _限制条件：不要过度获取（over-fetch）。只拉取对本次局部审查切实相关的上下文。_

### 步骤 2：局部微观审查（分析维度）

仔细评估目标范围内的代码，重点关注以下三个维度，并在过程中做好记录：

#### 2.1 健全性（正确性与鲁棒性）

- **逻辑与性能**：错误的条件判断、边界值错误、不必要的 O(n²) 算法、N+1 查询、未处理的边缘情况。
- **安全风险**：注入漏洞、未过滤的输入、硬编码敏感信息、反序列化风险、缺少鉴权。
- **鲁棒性**：未捕获的异常/错误路径、静默失败、在高并发/并发访问时缺失重试或超时机制、资源泄露（未关闭的文件或连接）。

#### 2.2 规范与约定

- **职责边界**：文件或函数是否承担了过多不相关的职责？一个简单的事情是否被无谓地拆分到了多个文件中？
- **风格一致性**：即使没有 Linter 强制约束，代码是否符合你在步骤 1 中观察到的项目既定风格（命名、错误处理惯例、注释风格等）？
- **最佳实践**：不要存在死代码、冗余注释或未关联工单的 `TODO`。

#### 2.3 精简度（最高优先级维度）

核心提问：**在不损失实际功能的前提下，这段代码能否写得更简单？** 重点搜寻以下倾向：

- **冗余变量声明**：引入了一个中间变量，但实际上该变量可以直接内联或用原始表达式代替；或多个变量持有几乎相同的值却无实际状态流转。
- **低价值的过度封装**：仅被使用一次的 1-2 行极短函数。为了所谓的“整洁”而提取，却增加了阅读时的跳转成本，且不具备复用性和可测试性。
- **中继/传递函数**：只负责调用另一个函数、不带任何校验、转换或分支处理的函数，平白拉长了调用链。
- **重复造轮子**：手写了标准库、已引入第三方库或项目中已有的工具函数可以直接实现的逻辑。

### 步骤 3：宏观架构适配审查

跳出代码行级别的细节，站在更高维度评估：

- **职责越界**：代码是否放错了层级（例如在 UI/视图层处理业务逻辑，在控制器中直接读写数据库）？
- **抽象层级**：该抽象是否与实际使用场景相匹配？（是否存在为单个调用者设计的过度泛化，或多处重复的手工实现？）
- **模式冲突**：它是否引入了与项目中现有同类模式/依赖相冲突的新方案？

### 步骤 4：交付审查发现

生成结构化的 Markdown 报告。**关键约束：绝对不要输出社交寒暄或前置废话（例如“好的，这是审查结果”）。请直接输出以下格式。**
保持简洁、易读且极具针对性。按影响严重程度排序，而非行号。

```markdown
## 代码审查报告：<Confirmed Scope>

### 🎯 概述

<1-3 句话：总体结论以及最需要修改的核心问题，若无则写明总体评价良好。>

### 🔴 正确性与鲁棒性

_(若无此维度问题，请直接删除此标题，下同)_

- `[严重程度]` **<问题发现>** — `path/to/file:line` — <问题危害> — <具体修改建议>

### 🟡 规范与约定

- **<问题发现>** — <具体修改建议>

### 🟢 精简度（简化建议）

- **<问题发现>** — 代替方案：`<具体的代码重构/内联建议>`

### 🏛️ 宏观架构适配性

- <评估这部分代码在系统中的分量与合理性，是否合适？>

### ✅ 亮点/优秀实践

- <1-2 条指出代码中写得好的地方，保持客观和鼓励，避免纯负面反馈>

### 📋 推荐修改清单（按优先级排序）

1. <最紧急/最重要的修复项>
2. <次要修复项/优化项>
```
